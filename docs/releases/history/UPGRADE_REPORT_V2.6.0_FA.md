# گزارش ارتقای عمیق SYSTEM v2.6.0

## خلاصهٔ اجرایی

در نسخهٔ 2.6.0 یک بخش مستقل دیگر از کنترل‌گر بزرگ قدیمی خارج شد: قواعد ثبت Activity، اعتبارسنجی شواهد یادگیری، نرمال‌سازی شمارنده‌های مادام‌العمر و خلاصه‌سازی تاریخچه اکنون در هستهٔ خالص TypeScript قرار دارند. کنترل‌گر قدیمی همچنان مسئول سازگاری با UI و `localStorage` است؛ بنابراین قالب ذخیره و کلیدهای قدیمی برای این ارتقا تغییر نکردند.

این نسخه مهاجرت IndexedDB را فعال نمی‌کند، APK تولید نمی‌کند و ادعا نمی‌کند آزمون حقیقی مرورگر در محیط محدودشده موفق شده است.

## یافته و اصلاح مهم

### ۱. مالکیت منطق در کنترل‌گر قدیمی

`js/legacy/app-controller.js` در نسخهٔ 2.5.0 حدود 5,297 خط داشت. بعد از استخراج بخشی از قواعد Activity و شمارنده‌ها، این فایل به 5,223 خط کاهش یافت. کاهش 74 خط به‌تنهایی هدف نیست؛ هدف اصلی این است که قواعد داده و اعتبارسنجی یک مالک تست‌پذیر داشته باشند.

### ۲. ماژول خالص TypeScript

ماژول تازهٔ `src/core/activity-ledger.ts` این مسئولیت‌ها را انجام می‌دهد:

- اعتبارسنجی و محدودسازی شناسه‌ها و متن‌های Activity، XP، Coins، Stat و داده‌های کمکی؛
- مدیریت شمارنده‌های مجاز مادام‌العمر و محدودسازی مقادیر نامعتبر یا بیش از حد؛
- حفظ رکوردهای قدیمی سازگار و محدود نگه‌داشتن تاریخچه به 300 رکورد؛
- ثبت شواهد یادگیری، مانند روش تمرین، نمره، زمان و نتیجهٔ خوداظهاری، بدون تغییر XP یا Coins؛
- تهیهٔ فهرست، خلاصه و بازهٔ زمانی برای داشبورد و AI planning محلی.

این ماژول DOM، `localStorage`، IndexedDB یا اتصال شبکه را نمی‌خواند. بنابراین می‌توان قوانین آن را جدا از رابط و بدون دسترسی به دادهٔ واقعی کاربر آزمود.

### ۳. مرز امن ذخیره‌سازی

در روش قبلی، رکورد Activity ابتدا در آرایهٔ حافظه اضافه یا تغییر داده می‌شد و سپس نوشتن `localStorage` انجام می‌گرفت. اگر ذخیره‌سازی به‌دلیل سهمیه یا محدودیت مرورگر شکست می‌خورد، وضعیت حافظه می‌توانست موقتاً با دادهٔ پایدار اختلاف پیدا کند.

در نسخهٔ جدید، آداپتر ابتدا یک نسخهٔ پیشنهادی از تاریخچه می‌سازد، نوشتن ذخیره‌گاه را اجرا می‌کند و تنها پس از موفقیت، مرجع حافظه را تغییر می‌دهد. همین اصل برای افزودن شواهد یادگیری رعایت شده است. آزمون رگرسیون خطای ساختگی ذخیره‌گاه را وارد می‌کند و بررسی می‌کند که رکورد یا شواهد ناتمام وارد تاریخچهٔ جاری نشود.

### ۴. حفظ سازگاری

- کلیدهای موجود مانند `system_v2_progress` و `system_v2_progress_history` حفظ شده‌اند.
- شکل داده‌های اصلی Player، Stat، Skill و Backup تغییر نکرده است.
- تاریخچهٔ قدیمی تا جایی که ساختار پایهٔ timestamp/title آن معتبر باشد حفظ می‌شود؛ داده‌های جانبی شناخته‌نشده به‌طور خودکار حذف نمی‌شوند.
- در این نسخه منبع فعال UI همچنان `localStorage` است. `src/storage/indexeddb.ts` و مهاجرت اختیاری آن هنوز جدا و مرحله‌بندی‌شده‌اند.
- جاوا و ساختار موجود Android جایگزین نشده‌اند؛ دارایی‌های وب به‌روز در پوشهٔ Android کپی شده‌اند.

| آزمون‌های جدید Activity Ledger | موفق؛ ورودی خراب، حد عددی، شواهد غیرقابل‌تغییر تا commit، تاریخچهٔ 300 رکوردی، بازهٔ زمانی و خلاصه‌سازی بررسی شد |
| آزمون‌های یکپارچهٔ حافظه/ذخیره‌گاه | موفق؛ نوشتن ناموفق Activity یا شواهد نباید در حافظه باقی بماند |

| `npm run test:e2e` | اجرا نشد؛ وابستگی محلی `@playwright/test` نصب نیست. خود آزمون‌ها موجودند و workflow CI نصب Playwright/Chromium را درخواست می‌کند. |
| APK واقعی | ساخته نشد؛ `prepare:android` فقط دارایی وب را آماده می‌کند. ساخت APK باید جداگانه با Android SDK و Gradle یا GitHub Actions انجام شود. |

## محدودیت‌های باقی‌مانده و قدم بعدی

1. `js/legacy/app-controller.js` هنوز بزرگ است؛ مرحلهٔ بعدی باید یک قابلیت مستقل دیگر، مانند اتصال Snapshot یا فرمان‌های Quest، را با آزمون رگرسیون استخراج کند.
2. آزمون واقعی IndexedDB باید در GitHub Actions یا مرورگری اجرا شود که طبق سیاست مجاز به بازکردن `localhost` باشد. تا وقتی این دروازه سبز نشده، تغییر مرجع ذخیره‌سازی UI ممنوع است.
3. پس از سبزشدن دروازه، مهاجرت محدود باید preview، جلوگیری از اجرای دوباره، حفظ `localStorage` قدیمی و راه بازیابی آزموده‌شده داشته باشد.

**نتیجه:** نسخهٔ 2.6.0 مالکیت منطق Activity Ledger را روشن‌تر و خطای همگام نبودن حافظه با ذخیره‌گاه را کاهش می‌دهد، بدون این‌که ساختار دادهٔ قدیمی کاربر را با مهاجرت ناگهانی به خطر بیندازد.
