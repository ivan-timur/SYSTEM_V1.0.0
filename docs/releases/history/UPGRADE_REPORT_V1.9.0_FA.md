# گزارش ارتقای SYSTEM v1.9.0

## Unified TypeScript Quest Reward Commands

**وضعیت:** ساخت و مجموعهٔ آزمون‌های خودکار موفق؛ آزمون واقعی مرورگر و ساخت APK در این محیط تکمیل نشدند.

## هدف این نسخه

در نسخهٔ 1.8.0، مهاجرت امن اطلاعات قدیمی و مسیر مرکزی پاداش‌ها موجود بود، اما اعتبارسنجی ورودی، ساخت شناسهٔ دامنه‌ای Quest و ساخت شناسهٔ جلوگیری از پرداخت مجدد هنوز تا حدی در JavaScript باقی مانده بود. در نسخهٔ 1.9.0 یک قرارداد خالص TypeScript برای این تصمیم‌ها ساخته شد و پیش از هر تغییر Player/Stat/Skill/History در مسیر زندهٔ پاداش اجرا می‌شود.

## تغییرات پیاده‌سازی‌شده

### 1. قرارداد مرکزی TypeScript

فایل `src/core/reward-command.ts` اضافه شد. این ماژول ورودی‌های شش مسیر را یکسان‌سازی می‌کند:

- Daily Quest
- AI Daily Quest
- Custom Quest
- Boss Quest
- Goal
- Goal evidence completion

این قرارداد نوع پاداش، شناسهٔ Quest/Goal، تاریخ محلی مأموریت روزانه، عنوان، XP، Coins، Stat و ارتباط Skill با Stat را اعتبارسنجی می‌کند. مقادیر عددی از سقف عددی فعلی برنامه بالاتر نمی‌روند و عملیات نامعتبر پیش از شروع هر تغییر پیشرفت رد می‌شوند.

### 2. هویت پایدار از TypeScript

تابع `getProgressionRewardIdentity()` شناسهٔ قطعی جلوگیری از پرداخت مجدد را می‌سازد. Goal دستی و تکمیل Goal از راه شواهد عمداً از یک شناسه استفاده می‌کنند تا دو مسیر مختلف نتوانند برای یک Goal دو بار پاداش بدهند. شناسهٔ Domain Quest نیز به‌صورت مرکزی تولید می‌شود.

در برنامهٔ زنده، `js/core/progression-idempotency.js` این شناسه را از API TypeScript می‌گیرد. پیاده‌سازی مستقل داخل آن فایل فقط به‌عنوان سازگاری برای تست‌ها و محیط‌های قدیمی که TypeScript بارگذاری نشده است نگه داشته شده است.

### 3. اتصال به مسیر واقعی پاداش‌ها

`js/legacy/app-controller.js` پیش از تغییر داده‌ها، ورودی را از `prepareProgressionReward()` عبور می‌دهد. سپس همان مسیر مرکزی موجود، محاسبهٔ Player XP/Level/Coins را با `completeQuest()` انجام می‌دهد و آداپترهای فعلی برای Stat، Skill، تاریخچه و rollback را حفظ می‌کند.

این تغییر مسیرهای مختلف را به یک قرارداد ورودی و هویتی مشترک متصل می‌کند، اما هنوز به معنی انتقال کل پایگاه داده یا تمام آثار جانبی به یک تراکنش IndexedDB نیست.

### 4. حفظ سازگاری

- ذخیره‌های `localStorage` و شکل داده‌های قدیمی حذف یا بازنویسی نشدند.
- رابط و منطق تجربهٔ کاربر بی‌دلیل بازطراحی نشدند.
- هر 11 شناسهٔ تم فعلی حفظ شدند.
- مهاجرت IndexedDB همچنان اختیاری است و در شروع برنامه خودکار اجرا نمی‌شود.

## آزمایش‌های انجام‌شده

فرمان `npm test` با موفقیت کامل شد، شامل:

- ساخت TypeScript و Runtime
- 38 بررسی قرارداد فرمان پاداش برای هر شش مسیر و داده‌های نامعتبر
- تست Bridge زندهٔ `completeQuest()` و مسیر واقعی پاداش برای هر شش نوع Quest/Goal
- تست جلوگیری از پاداش تکراری
- آزمون‌های محاسبات XP/Level، شامل 1,531 بررسی
- آزمون‌های مهارت و برنامهٔ درسی: 1,335 بررسی روی 583 گره
- آزمون اعتبارسنجی JSON، ذخیره‌سازی، Backup، امنیت، UI، Goal و همهٔ تم‌ها
- آزمون یکپارچگی انتشار نسخهٔ 1.9.0

همچنین `npm run prepare:android` موفق شد و 128 فایل با حجم تقریبی 5.94 MiB به دارایی‌های Android کپی شدند. یک سرور HTTP محلی نیز اجرا شد؛ مسیرهای `index.html`، `js/app.js`، خروجی جدید `dist/ts/core/reward-command.js`، هستهٔ progression، کد runtime، `sw.js` و `manifest.webmanifest` همگی پاسخ HTTP 200 دادند.

## آزمون‌هایی که تکمیل نشدند

- `npm run test:e2e` اجرا شد، اما اسکریپت اعلام کرد وابستگی توسعه‌ای `@playwright/test` در محیط نصب نیست؛ بنابراین آزمون End-to-End مرورگر اجرا نشد.
- `npm run test:browser-idb` اجرا شد، اما Chromium در محیط به‌علت محدودیت محیط گرافیکی/D-Bus شروع کامل نشد و آزمون IndexedDB پیش از پایان timeout شد. این نتیجه موفق محسوب نشده است.
- APK واقعی ساخته یا روی دستگاه Android نصب و اجرا نشده است.

## مرز معماری این نسخه

مرجع فعلی ذخیره‌سازی رابط قدیمی همچنان `localStorage` است. قرارداد مشترک TypeScript و محاسبات مرکزی Player اکنون در مسیر زنده قرار دارند، اما انتقال تمام Statها، Skillها، شمارنده‌های پیشرفت، تاریخچه، پاداش تصادفی Daily Prize و وضعیت Quest به یک تراکنش واحد IndexedDB هنوز انجام نشده است. این مرحله عمداً جدا نگه داشته شده تا از دو منبع هم‌زمان برای پاداش و اختلاف داده‌ها جلوگیری شود.

## گام منطقی بعدی

مرحلهٔ بعد باید یک آداپتر تراکنش واحد با پشتیبانی از همهٔ آثار جانبی بسازد و برایش آزمون واقعی مرورگر قابل‌اجرا فراهم کند؛ سپس انتقال منبع اصلی ذخیره‌سازی از `localStorage` به IndexedDB پس از پیش‌نمایش، Backup و مهاجرت قابل‌بازگشت انجام شود. تا آن زمان، مسیر legacy نباید ادعای atomicity کامل پایگاه‌داده داشته باشد.
