# گزارش تحلیل عمیق و ارتقای SYSTEM v2.5.0

## نتیجهٔ اجرایی

نسخهٔ 2.5.0 یک ارتقای معماری مرحله‌ای است، نه بازنویسی پرخطر کل برنامه. مهم‌ترین تغییر اجرایی این است که معیارهای بازشدن هشت Achievement پویا از شرط‌های پراکنده در کنترل‌گر قدیمی به هستهٔ خالص TypeScript منتقل شده‌اند. یک نگهبان خودکار معماری نیز به آزمون‌ها و بررسی سلامت پروژه اضافه شده تا مرزهای مهم در تغییرات بعدی فراموش نشوند.

**هیچ ادعایی مبنی بر مهاجرت کامل به IndexedDB، مهاجرت Android به Kotlin، ساخت سرور هوش مصنوعی یا تولید APK در این نسخه وجود ندارد.** این موارد تنها پس از اثبات نیاز و عبور از آزمون‌های مناسب انجام می‌شوند.

## یافته‌های اصلی بررسی پروژهٔ v2.4.0

### ۱. معماری دو مرحله‌ای بود

هستهٔ TypeScript برای پیشرفت، فرمان‌های پاداش، کاتالوگ Quest و IndexedDB وجود داشت؛ در عین حال، بخش بزرگی از جریان رابط و تعدادی از تصمیم‌های تجارتی هنوز در `js/legacy/app-controller.js` بودند. این یعنی مالکیت برخی قوانین به‌صورت کامل از کنترل‌گر قدیمی جدا نشده بود.

### ۲. معیارهای Achievement در کنترل‌گر قدیمی تکرار می‌شدند

قانون‌های First Mission، Quest Adept، Streak، Boss Slayer، Skill Seeker و Quest Architect به‌صورت شرط‌های مستقیم JavaScript نگه‌داری می‌شدند؛ Level Five نیز با حداقل سطح روی تعریف پاداش سنجیده می‌شد. این باعث می‌شد معماری هدف «TypeScript مالک منطق Achievement» تنها به بخشی از موتور دامنه محدود باشد.

### ۳. IndexedDB هنوز منبع زندهٔ رابط نیست

طرح پایگاه داده و API مهاجرت وجود دارد، اما رابط فعلی همچنان به `localStorage` متکی است. این محافظه‌کاری در حال حاضر درست است: قطع زودهنگام ذخیرهٔ قدیمی می‌تواند XP، Coins، Stat، Skill، streak، Daily Prize یا Backup کاربر را تحت خطر قرار بدهد.

### ۴. برخی فناوری‌ها هنوز ضرورت اجرایی ندارند

کد بومی Android اکنون Java است. افزودن Kotlin، SQLite، Canvas/WebGL، Python به runtime، سرور FastAPI/Node، Rust/WASM یا ICU MessageFormat به‌خودی‌خود کیفیت سیستم را بالا نمی‌برد. تا وقتی نیاز مشخص، فایدهٔ قابل‌اندازه‌گیری و آزمون نگه‌داری وجود نداشته باشد، واردکردن آن‌ها هزینه و سطح پیچیدگی را زیاد می‌کند.

## تغییرهای این نسخه

### هستهٔ معیارهای Achievement

- فایل تازهٔ `src/core/achievements.ts` هشت شناسهٔ پایدار و معیارهای رسمی بازشدن آن‌ها را نگه‌داری می‌کند.
- ورودی snapshot بررسی می‌شود: شمارنده‌ها باید عدد صحیح امن و غیرمنفی باشند و Level بازیکن حداقل ۱ باشد.
- شناسهٔ ناشناخته، مقدار خراب یا API غایب باعث بازشدن پاداش نمی‌شود؛ رفتار در وضعیت نامطمئن «رد» است.
- `js/app.js` API منجمد `SYSTEMTypeScriptAchievements` را به کنترل‌گر سازگاری می‌دهد.
- `canClaimReward()` اکنون شرط‌های پویا را به TypeScript واگذار می‌کند. حداقل سطح عمومی در JavaScript فقط برای پاداش‌های غیرپویا اعمال می‌شود تا شرط Level Five در دو جا تکرار نشود.
- شناسه‌ها، کارت‌های پاداش، روش claim، ساختار ذخیرهٔ قدیمی و شیوهٔ نمایش پاداش‌ها تغییر نکردند.

### نگهبان معماری

اسکریپت `scripts/architecture-guard.js` بررسی می‌کند که:

- نسخه‌های کلیدی با `VERSION` هماهنگ باشند؛
- ورود برنامه از ES Module باشد و APIهای TypeScript را ارائه کند؛
- XP/Level/Rank/Quest در هستهٔ TypeScript تعریف شوند؛
- هشت معیار Achievement در TypeScript باشند و شرط‌های مشابه دوباره در کنترل‌گر JavaScript نوشته نشده باشند؛
- اعتبارسنجی JSON، قرارداد فرمان پاداش و مرز مهاجرت IndexedDB وجود داشته باشد؛
- نقشهٔ معماری همهٔ فناوری‌های مورد نظر و وضعیت واقعی آن‌ها را مستند کرده باشد.

این نگهبان از اجرای آزمون‌های واقعی مرورگر یا APK دفاعی جایگزین نمی‌شود؛ وظیفه‌اش بررسی خودکار مرزهای معماری در سورس است.

### اسناد معماری

- `docs/ARCHITECTURE.md`: اصل‌های منبع معتبر و مالکیت لایه‌ها.
- `docs/ARCHITECTURE_ROADMAP_FA.md`: نقشهٔ فناوری‌ها، وضعیت فعلی و مراحل انتقال با شرط قبولی.
- `docs/STRUCTURE.md`: ساختار پوشه‌ها، جریان شروع و گردش کار آزمون به‌روز شد.

### ساخت و خروجی Android

- نسخه از `2.4.0` به `2.5.0` ارتقا یافت.
- خروجی TypeScript، CSS و Service Worker بازسازی شد.
- پس از ساخت، آینهٔ وب Android از سورس به‌روز شد: ۱۳۲ فایل، حدود ۵٫۹۹ MiB.
- این مرحله فقط دارایی‌های وب Android را آماده می‌کند؛ به‌خودی‌خود APK نمی‌سازد.

## دستورهای بعدی در محیط توسعه

برای بررسی منطق و معماری:

```bash
npm test
npm run doctor
npm run architecture:check
```

برای آماده‌سازی دارایی‌های Android و سپس ساخت APK در محیط دارای SDK:

```bash
npm run prepare:android
cd android
gradle --no-daemon assembleDebug
```

برای آزمون حقیقی IndexedDB و تعامل رابط، وابستگی‌های npm و Chromium Playwright باید در محیط مجاز نصب شوند؛ موفقیت آزمون ایستا به‌تنهایی برای مهاجرت زندهٔ ذخیره‌سازی کافی نیست.

## ترتیب پیشنهادی نسخه‌های بعدی

۱. ادامهٔ استخراج قابلیت‌های کوچک از کنترل‌گر بزرگ با آزمون رگرسیون برای هر مرحله. ۲. اجرای موفق آزمون IndexedDB واقعی در CI. ۳. مهاجرت فقط یک مسیر محدود به IndexedDB با preview و rollback. ۴. سپس ارزیابی نیاز بومی Kotlin یا ذخیره‌سازی SQLite؛ نه پیش از آن.
