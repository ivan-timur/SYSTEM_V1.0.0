# گزارش ارتقای SYSTEM v1.2.0 — هستهٔ پیشرفت تراکنشی

## هدف این پله

در این نسخه به‌جای بازنویسی پرخطر کنترل‌گر بزرگ قدیمی، مرزهای هستهٔ پیشرفت TypeScript محکم‌تر شده و یک مسیر کامل‌تر برای ثبت اتمی نتیجهٔ مأموریت در IndexedDB اضافه شده است. ذخیره‌سازی قدیمی `localStorage` و قالب نسخه‌های پشتیبان عمداً تغییر نکرده‌اند.

## کارهای انجام‌شده

- اعتبارسنجی وضعیت بازیکن، سطح، XP، سکه‌ها، مهارت‌ها، وضعیت مأموریت، پاداش‌ها، زمان تکمیل، قانون سطح و رتبه.
- جلوگیری از تغییر شیء ورودی؛ نتیجه در یک نسخهٔ مستقل محاسبه می‌شود.
- جلوگیری از پاداش تکراری با نشانگر تکمیل مأموریت و شناسهٔ یکتای رویداد XP.
- تشخیص وضعیت ناسازگار میان بازیکن، مأموریت و دفتر XP در مسیر IndexedDB؛ در این حالت تراکنش لغو می‌شود، نه اینکه XP دوباره اعطا شود.
- خواندن بازیکن، مأموریت و رویداد XP در یک تراکنش `readwrite` و نوشتن نتیجه، مأموریت تکمیل‌شده، دفتر XP، مهارت‌ها و دستاوردهای تازه در همان تراکنش.
- افزودن آزمون‌های TypeScript برای چند سطح در یک رویداد، ورودی نامعتبر، عدم تغییر ورودی، شناسه‌های تکراری و قرارداد تراکنش ذخیره‌سازی.
- بازسازی خروجی CSS و Service Worker و همگام‌سازی دارایی‌های وب با پوستهٔ Android.

## نتایج بررسی

- `npm test`: موفق؛ آزمون TypeScript و تمام آزمون‌های ایستای فهرست‌شدهٔ پروژه موفق شدند.
- `npm run doctor`: موفق؛ فراداده و فایل‌های الزامی سازگارند.
- `npm run prepare:android`: موفق؛ ۱۱۹ فایل وب در دارایی‌های Android همگام شدند.
- وابستگی Playwright در محیط اجرا نصب نبود و نصب npm در این محیط به پایان نرسید؛ بنابراین آزمون واقعی Playwright و مشاهدهٔ بصری در مرورگر تأیید نشده‌اند.

## محدودیت مهم و مرحلهٔ بعد

این مسیر IndexedDB هنوز به دکمه‌های واقعی مأموریت در کنترل‌گر قدیمی متصل نشده و پایگاه دادهٔ جدید نیز به‌طور خودکار از ذخیره‌های کاربر seed یا مهاجرت نمی‌شود. این عمدی است: اجرای هم‌زمان موتور قدیمی و جدید می‌تواند دوبار XP بدهد یا شکل ذخیره را ناسازگار کند. پس در این نسخه ادعا نمی‌شود که منطق تمام مأموریت‌های رابط کاربری از هستهٔ TypeScript عبور می‌کند.

مرحلهٔ بعد باید یک adapter سازگاری مشخص برای یک نوع مأموریت انتخاب کند، شکل دادهٔ واقعی آن را با schema اعتبارسنجی کند، از ذخیرهٔ فعلی نسخهٔ پشتیبان بگیرد، مسیر مهاجرت قابل‌برگشت اضافه کند و تنها پس از آزمون مرورگر/Android همان نوع مأموریت را به هستهٔ جدید منتقل کند. سپس این کار برای نوع بعدی تکرار شود.
