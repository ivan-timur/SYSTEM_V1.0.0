# گزارش اصلاحات عمیق SYSTEM v9.3.2

**وضعیت:** اصلاحات سورس و آزمون‌های ایستای پروژه انجام شد. ساخت APK و E2E مرورگر در همین محیط قابل تأیید نبود و باید در GitHub Actions / Android SDK اجرا شود.

## اصلاحات انجام‌شده

### ۱. به‌روزرسان بومی اندروید
- رویدادهای ارسالی از Java به WebView دیگر JSON خام را مستقیم در کد اجرایی قرار نمی‌دهند؛ کل payload ابتدا با `JSONObject.quote` نقل‌قول‌گذاری و سپس در صفحه با `JSON.parse` بازیابی می‌شود.
- آدرس تغییرمسیر دانلود اکنون باید HTTPS، بدون user-info و با پورت استاندارد باشد و میزبان آن با فهرست مشخص میزبان‌های GitHub Releases مطابقت داشته باشد.
- فایل APK معلق برای نصب پس از بازگشت از تنظیمات، از نظر مسیر canonical، محل ذخیره، نام نسخه و هدر فایل بررسی می‌شود.
- فایل SHA-256 باید علاوه بر digest معتبر، نام دقیق همان APK را در خود داشته باشد؛ checksum نامرتبط باعث توقف به‌روزرسانی می‌شود.
- مسیر نصب APK نیز همان بررسی محل/نام/هدر را انجام می‌دهد تا مسیر ذخیره‌شدهٔ نامعتبر به نصب‌کننده تحویل نشود.
- توکن GitHub به حداکثر ۵۱۲ نویسه محدود شده است. اگر متن رمزنگاری‌شده خراب یا با Android Keystore فعلی غیرقابل‌بازیابی شود، نشانگر ذخیره‌شده و کلید معیوب حذف می‌شوند تا کاربر بتواند توکن تازه وارد کند.
- حذف توکن، وضعیت نصب معلق را نیز پاک می‌کند.

### ۲. رابط به‌روزرسانی دوزبانه
- متن‌های اصلی صفحهٔ به‌روزرسانی و وضعیت‌های تشخیصی اکنون با رویداد تغییر زبان میان انگلیسی و دری بازنمایی می‌شوند.
- متن توضیحات انتشار با `textContent` نشان داده می‌شود و به‌عنوان HTML اجرا نمی‌شود.
- وضعیت دکمه‌ها، وضعیت خطا و پیام‌های به‌روزرسانی پس از تغییر زبان مجدداً رسم می‌شوند.

### ۳. خط لولهٔ CI / ساخت
- گردش‌کار ساخت APK دستی پیش از بسته‌بندی، `npm test` و `npm run doctor` را اجرا می‌کند.
- گردش‌کار انتشار Release ابتدا وابستگی آزمون را نصب می‌کند، آزمون‌های ایستا و سلامت پروژه را اجرا می‌کند، Chromium مربوط به Playwright را نصب می‌کند و سپس آزمون‌های واقعی مرورگر را اجرا می‌کند. در صورت شکست این دروازه‌ها، مرحلهٔ ساخت و انتشار APK انجام نمی‌شود.
- نام نسخه و checksum انتشار همچنان از نسخهٔ canonical و APK امضاشده ساخته می‌شود.

### ۴. مستندات و همگام‌سازی
- نسخهٔ canonical پروژه به `9.3.2` ارتقا یافت.
- `package.json`، نسخهٔ Android، manifest، JavaScript، Service Worker و README از `VERSION` همگام می‌شوند.
- راهنمای Android و README با نسخه و مراحل Release فعلی هماهنگ شدند.
- فایل‌های وب داخل `android/app/src/main/assets/www/` از خروجی نهایی پروژه دوباره ساخته شدند.

## آزمون‌های اجراشده

| آزمون | نتیجه |
|---|---|
| `npm test` | موفق؛ مجموع ۳٬۶۵۶ بررسی/assertion دارای شمارش صریح؛ آزمون تنظیمات به‌روزرسانی Android نیز جداگانه موفق شد |
| `npm run doctor` | موفق؛ فایل‌های runtime و فرادادهٔ نسخه سازگارند |
| `npm run prepare:android` | موفق؛ ۱۱۶ فایل وب، حدود ۵٫۶۷ MiB، همگام شد |
| ساخت CSS | موفق؛ ۵۹ منبع، صفر `!important` در خروجی نهایی |
| ساخت Service Worker | موفق؛ ۱۱۷ منبع precache |
| بررسی نحوی JavaScript | موفق؛ ۵۵ فایل |
| بررسی فرمت فایل | موفق؛ ۲۴ JSON/Webmanifest، پنج XML و سه Workflow YAML |
| `npm run test:e2e` در همین محیط | اجرا نشد؛ وابستگی npm به‌علت خطای DNS در دسترس نبود و مرورگر این محیط ناوبری محلی را مسدود کرد |
| کامپایل APK واقعی | انجام نشد؛ Android SDK و Gradle در محیط حاضر نصب نیستند |
| نصب/به‌روزرسانی روی گوشی واقعی | انجام نشد |

## محدودیت‌های باقی‌مانده

- نتیجهٔ واقعی Playwright باید توسط گردش‌کار GitHub Actions تأیید شود؛ افزودن مرحله به workflow به‌معنای اجرای موفق آن در GitHub نیست.
- APK امضاشده باید در runner دارای Android SDK ساخته شود. برای Release، چهار Secret امضای Android باید از قبل تنظیم شده باشند.
- فرایند به‌روزرسانی خصوصی نیازمند توکن Fine-grained دارای دسترسی فقط‌خواندنی `Contents` به `ivan-timur/SYSTEM_V1.0.0` است.
- نصب نهایی همچنان توسط Package Installer اندروید و با تأیید کاربر انجام می‌شود؛ نصب بی‌صدا پشتیبانی نمی‌شود.

## انتشار پیشنهادی

۱. ZIP را استخراج کن و همهٔ تغییرات را در شاخهٔ آزمایشی مخزن خصوصی بررسی کن.
۲. Workflow کیفیت را اجرا کن و مطمئن شو همهٔ آزمون‌های مرورگر موفق‌اند.
۳. Workflow ساخت دستی APK را اجرا و APK آزمایشی را روی دستگاه نصب کن.
۴. پس از تنظیم/بررسی کلید امضای ثابت، تگ تازهٔ `v9.3.2` را در مخزن منتشر کن تا workflow انتشار امضاشده اجرا شود.
۵. از نسخهٔ امضاشده نسخهٔ پشتیبان نصب بگیر و چرخهٔ ارتقا از نسخهٔ قبلی به `9.3.2` را آزمایش کن. پیشرفت محلی برنامه را قبل از آزمایش با Backup ذخیره کن.
