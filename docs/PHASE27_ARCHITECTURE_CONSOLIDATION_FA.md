# فاز ۲۷ — تثبیت مرزهای معماری SYSTEM

## هدف
این فاز نقشهٔ فناوری‌ها را به قواعد قابل‌بررسی تبدیل می‌کند. هدف افزودن فناوری‌های تازه نیست؛ هدف جلوگیری از منطق تکراری، ذخیره‌سازی دوگانه، ادعاهای نادرست دربارهٔ آمادگی انتشار و مهاجرت پرخطر است.

## تصمیم‌های تثبیت‌شده

1. **هستهٔ منطق:** TypeScript مالک قواعد XP، Level، Rank، Quest، Achievement و برنامه‌ریزی تکمیل مأموریت است. JavaScript رابط و سازگاری را هماهنگ می‌کند و نباید محاسبهٔ موازی XP ایجاد کند.
2. **مرجع دادهٔ فعال:** تا زمان عبور از دروازهٔ مرورگر واقعی و آزمون بازیابی، مسیر فعال قدیمی `localStorage` حفظ می‌شود. IndexedDB و APIهای پایدار آن آماده‌سازی شده‌اند، اما این به معنای cutover کامل رابط نیست.
3. **مهاجرت داده:** فقط از مسیر `preview → approve → migrate` با بررسی تازگی داده، تأیید هشدارها و حفظ دادهٔ قدیمی انجام شود. نوشتن دوگانهٔ کنترل‌نشده ممنوع است.
4. **کاتالوگ‌ها:** JSON برای دادهٔ اولیه است؛ دادهٔ ذخیره‌شدهٔ کاربر را جایگزین نمی‌کند. هر ورودی خارجی یا واردشده باید اعتبارسنجی شود.
5. **Android:** WebView فعلی و کد Java حفظ می‌شوند تا رفتار موجود آزموده شود. Kotlin برای قابلیت بومی جدید یا مهاجرت مرحله‌ای است؛ بازنویسی یک‌باره لازم نیست.
6. **رندر بصری:** Canvas صرفاً نمایشی است و مالک پیشرفت یا پاداش نیست. WebGL فقط پس از اندازه‌گیری و اثبات نیاز بررسی شود.
7. **سرور:** FastAPI و Node.js گزینه‌های جایگزین‌اند، نه دو سرور اجباری. تا زمانی که همگام‌سازی یا AI سمت سرور نیاز واقعی نباشد، سرویس آنلاین اضافه نمی‌شود.
8. **SQLite و Rust/WASM:** هر دو مشروط به نیاز و اندازه‌گیری‌اند و نباید برای نمایش فناوری وارد runtime شوند.
9. **چندزبانه‌سازی:** ICU MessageFormat یک مسیر توسعهٔ جداست؛ مهاجرت باید با آزمون زبان دری، RTL، متغیرها و قواعد جمع انجام شود.
10. **خروجی تولیدی:** فایل‌های `dist/ts/`، `css/system.css`، `sw.js` و آینهٔ Android از سورس ساخته شوند و دستی ویرایش نشوند.
11. **انتشار:** ساخت asset وب، ساخت APK، نصب APK و آزمون روی دستگاه چهار نتیجهٔ متفاوت‌اند؛ موفقیت یکی نباید جای دیگری گزارش شود.

## ترتیب اجرای پیشنهادی

### Gate A — هسته و جلوگیری از تکرار
- آزمون‌های XP، تکمیل Quest و پاداش تکراری اجرا شوند.
- مسیرهای UI که هنوز منطق تجاری در کنترل‌گر قدیمی دارند، در فهرست مهاجرت ثبت شوند.
- هر استخراج از کنترل‌گر با آزمون رگرسیون مستقل انجام شود.

### Gate B — دوام داده
- مسیرهای نوشتن `localStorage` و IndexedDB فهرست شوند.
- آزمون مرورگر واقعی IndexedDB در محیط مجاز اجرا شود.
- مهاجرت، بستن/بازکردن پایگاه، rollback و بازیابی Backup بررسی شوند.
- تا سبزشدن این موارد، cutover عمومی انجام نشود.

### Gate C — همگام‌سازی وب و Android
- `npm run build` و `npm run prepare:android` اجرا شوند.
- `npm run release:preflight` و آزمون‌های مرتبط اجرا شوند.
- ساخت APK با Gradle/Android Studio یا CI انجام شود.
- APK روی دستگاه نصب و مسیر راه‌اندازی، آفلاین، اعلان‌ها و نگهداری داده بررسی شود.

### Gate D — قابلیت‌های آینده
- ابتدا نیاز، ریسک، مالک داده و معیار پذیرش نوشته شود.
- سپس تنها یک گزینه انتخاب شود: سرور، SQLite، WebGL یا WASM.
- قابلیت جدید بدون آزمون و بدون تعریف مسیر بازیابی وارد انتشار نشود.

## وضعیت اعتبارسنجی این بسته

این فاز یک سند تصمیم معماری و آزمون قراردادی اضافه می‌کند. در محیط آماده‌سازی این بسته، `node_modules` نصب نبود؛ بنابراین این تغییر به‌تنهایی ادعای موفقیت کامل `npm test`، اجرای واقعی IndexedDB در مرورگر، ساخت APK یا آزمون دستگاه نمی‌کند. برای انتشار باید در محیط دارای Node.js/npm، وابستگی‌های نصب‌شده، ابزار Android و دستگاه آزمایشی، دروازه‌های مربوطه اجرا شوند.

## معیار پایان فاز

- قواعد تصمیم معماری مستند و در آزمون قراردادی کنترل شوند.
- هیچ فناوری مشروط به‌عنوان قابلیت فعال معرفی نشود.
- مرجع ذخیره‌سازی فعلی و محدودیت‌های مهاجرت صریح بمانند.
- ساخت APK و آزمون دستگاه به‌عنوان مراحل جداگانه ثبت شوند.
