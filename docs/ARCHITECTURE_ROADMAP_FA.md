# نقشهٔ معماری نهایی SYSTEM — برنامهٔ مهاجرت مرحله‌ای

این سند مقصد معماری را تعریف می‌کند؛ به معنی فعال‌بودن تمام فناوری‌ها در نسخهٔ فعلی نیست. اصل اصلی این است که هر قانون تجارتی یک منبع معتبر داشته باشد، رابط کاربری مالک منطق پیشرفت نشود و هیچ مهاجرت ذخیره‌سازی بدون آزمون واقعی و راه برگشت انجام نگیرد.

## ۱. نقشهٔ مسئولیت فناوری‌ها

| فناوری | مسئولیت نهایی | وضعیت فعلی / تصمیم |
|---|---|---|
| JavaScript | نقطهٔ ورود برنامه، راه‌اندازی ماژول‌ها و سازگاری با کد قدیمی | فعال؛ `js/app.js` نقطهٔ ورود است و `js/legacy/app-controller.js` هنوز تدریجی مهاجرت می‌کند. لایهٔ قدیمی اکنون بیشتر مسئول اتصال رابط و ذخیره‌سازی است. |
| TypeScript | هستهٔ واحد XP، Level، Rank، Quest، فرمان‌های پاداش، Achievement، Activity Ledger و قراردادهای قواعد مأموریت | فعال و در حال گسترش؛ منطق XP، معیارهای Achievement، اعتبارسنجی فعالیت‌ها و وضعیت Daily Quest در `src/core/` و قراردادهای Custom/Boss Quest در `src/features/quest-command.ts` و `src/features/quest-completion-plan.ts` نگه‌داری می‌شوند. |
| HTML / CSS | ساختار صفحات، دسترس‌پذیری، رابط کاربری و تم‌ها | فعال؛ `index.html` و فایل‌های منبع `css/` اصل و `css/system.css` خروجی تولیدشده است. |
| JSON | کاتالوگ‌های اولیه و تنظیمات قابل اعتبارسنجی | فعال به‌عنوان دادهٔ اولیه/مرجع؛ هر فایل JSON پیش از استفاده باید از اعتبارسنجی بگذرد. کاتالوگ‌های هنوز متصل‌نشده نباید به‌عنوان منبع زنده معرفی شوند. |
| IndexedDB | ذخیره‌سازی محلی ساختاریافته در مرورگر و تراکنش‌های اتمیک | آماده‌سازی‌شده، اما مرجع عمومی رابط هنوز `localStorage` است؛ انتقال زنده تا موفقیت آزمون واقعی مرورگر متوقف می‌ماند. |
| SQLite | ذخیره‌سازی بومی یا گزارش‌گیری ساختاریافته، در صورت نیاز اثبات‌شده | فعلاً استفاده نمی‌شود؛ فقط وقتی پرس‌وجوها/گزارش‌ها با IndexedDB و فایل خروجی به‌خوبی حل نشوند بررسی می‌شود. |
| Kotlin | قابلیت‌های بومی آیندهٔ Android | هنوز پیاده‌سازی نشده؛ ابتدا باید نیاز بومی روشن و API پل وب‌ویو تثبیت شود. |
| Java | کد فعلی Android تا مهاجرت امن | فعال؛ WebView، انتخاب/ذخیرهٔ فایل، یادآورها و به‌روزرسان بومی هنوز Java هستند. مهاجرت فوری لازم نیست. |
| Canvas / WebGL | Canvas برای جلوهٔ محیطی سبک و بازخورد رویدادها؛ WebGL فقط برای صحنهٔ گرافیکی واقعاً پیچیده | از نسخهٔ 3.1.0 یک Canvas تزئینی سبک پیاده شده و در نسخهٔ 3.2.0 بازخورد milestone و کنترل‌های تنظیمات اضافه شده‌اند؛ WebGL همچنان استفاده نمی‌شود. نرخ فریم و DPR محدود، حرکت با صفحهٔ مخفی متوقف، موبایل کم‌تراکم‌تر و `prefers-reduced-motion` رعایت می‌شود. Canvas مالک منطق بازی نیست و فقط ترجیحات بصری مستقل را ذخیره می‌کند. |
| Python | ابزارهای آفلاین تولید محتوا، تحلیل داده و کنترل توازن XP | هنوز بخشی از runtime نیست؛ در صورت افزایش نیاز به تولید/تحلیل محتوای دسته‌ای به‌عنوان ابزار توسعه افزوده می‌شود. |
| FastAPI یا Node.js | سرور اختیاری AI Coach و همگام‌سازی چند دستگاه | فعلاً وجود ندارد؛ فقط در صورت نیاز واقعی به همگام‌سازی، کنترل دسترسی یا مخفی‌ماندن اعتبارنامه‌ها ساخته می‌شود. |
| Rust / WebAssembly | محاسبات سنگین با سود قابل اندازه‌گیری | استفاده نمی‌شود و برنامه‌ای برای افزودن صرفاً نمایشی آن وجود ندارد. |
| Markdown / YAML / Shell | مستندات، تنظیمات CI، ساخت، آزمون و انتشار | فعال؛ جریان‌های GitHub Actions و اسناد پروژه در این لایه‌اند. |
| ICU MessageFormat | قالب‌بندی پیچیدهٔ متن چندزبانه، جمع و متغیرهای زبانی | فعلاً به تعویق است؛ سیستم ترجمهٔ جاری حفظ می‌شود تا مهاجرت بدون اختلال زبان دری/RTL آماده شود. |

## ۲. مرزهای معماری

1. **منبع منطق پیشرفت:** منطق XP/Level/Rank و انتقال تکمیل Quest در TypeScript است. JavaScript فقط ورودی/خروجی قدیمی و رابط را سازگار می‌کند.
2. **دادهٔ کاربر با کاتالوگ فرق دارد:** JSONهای seed کاتالوگ‌اند، نه جایگزین ذخیرهٔ فعال بازیکن. ورودی کاربر و Backup باید جداگانه اعتبارسنجی شوند.
3. **یک منبع معتبر برای معیار Achievement:** شرط بازشدن Achievementهای پویا در `src/core/achievements.ts` است. کنترل‌گر JS فقط snapshot را می‌سازد و نتیجه می‌گیرد؛ وضعیت claim و ارائهٔ کارت‌ها فعلاً در کد قدیمی می‌ماند.
4. **Activity Ledger از رابط جداست:** `src/core/activity-ledger.ts` رکورد فعالیت و شواهد یادگیری را اعتبارسنجی و خلاصه‌سازی می‌کند؛ کنترل‌گر فقط ذخیره‌سازی و اتصال را انجام می‌دهد. نوشتن رویداد یا شواهد باید در حافظه هم فقط پس از موفقیت نوشتن ذخیره‌گاه اعمال شود. شواهد یادگیری به‌خودی‌خود XP یا سکه ایجاد نمی‌کند.
5. **خروجی تولیدشده را دستی تغییر نده:** `dist/ts/`, `js/generated/progression-math.js`, `css/system.css`, `sw.js` و آینهٔ Android باید از سورس با اسکریپت build ساخته شوند.
6. **مهاجرت ذخیره‌سازی با حفظ اطلاعات:** تا وقتی آزمون حقیقی IndexedDB و مسیر بازیابی سبز نشده، `localStorage` فعال حذف یا کنار گذاشته نمی‌شود. Preview مهاجرت باید پیش از Apply قابل بررسی باشد.
7. **قابلیت بومی فقط پشت پل محدود:** Java/Kotlin نباید دوباره XP یا قوانین Quest را محاسبه کنند؛ آن‌ها فقط قابلیت سیستم‌عامل را ارائه می‌کنند.
8. **هوش مصنوعی اختیاری است:** برنامهٔ اصلی باید بدون اتصال AI همچنان قابل استفاده بماند. کلید ارائه‌دهنده نباید در سورس، ZIP، گزارش خطا یا ذخیرهٔ دائمی مرورگر قرار گیرد.

## ۳. ترتیب مهاجرت و دروازه‌های قبولی

### مرحلهٔ A — تثبیت مالکیت منطق (نسخهٔ 2.5.0)

- افزودن معیارهای Achievement به هستهٔ TypeScript و اتصال امن آن به کنترل‌گر موجود.
- افزودن آزمون‌های مرزی و نگهبان معماری برای جلوگیری از برگشت منطق پیشرفت به JS.
- حفظ شناسه‌های ذخیره‌شده، قالب Backup، روش پاداش‌دهی و منبع فعلی ذخیره‌سازی.

**شرط عبور:** آزمون‌های TypeScript و آزمون‌های سازگاری معیارهای Achievement موفق شوند.

### مرحلهٔ B — کوچک‌سازی کنترل‌گر قدیمی و استخراج Activity Ledger و Quest State (نسخه‌های 2.6.0 تا 2.8.0)

- هر بار فقط یک قابلیت مستقل استخراج شود: ابتدا لایهٔ نمایش/داده، سپس عملیات Quest، سپس Rewards.
- برای هر استخراج، آزمون قرارداد و رگرسیون افزوده شود؛ بازنویسی یک‌بارهٔ فایل بزرگ انجام نشود.
- در نسخهٔ 2.6.0، اعتبارسنجی رکوردهای Activity، شمارنده‌های مادام‌العمر، ثبت شواهد یادگیری و خلاصه‌سازی به `src/core/activity-ledger.ts` منتقل شده‌اند؛ کنترل‌گر قدیمی تنها عملیات ذخیره و سازگاری را نگه می‌دارد.
- در نسخهٔ 2.7.0، خواندن/نرمال‌سازی وضعیت Daily Quest و ساخت ورودی‌های ذخیره‌سازی به `src/storage/legacy-daily-quest-state.ts` منتقل شده است. کلیدهای قدیمی و `SYSTEMStorage` به‌عنوان آداپتور ذخیره حفظ شده‌اند.
- شناسه‌ها و ترتیب راه‌اندازی فعلی تا اثبات سازگاری حفظ شوند.

**شرط عبور:** رفتار صفحه، XP، Coins، Stats، Skills، streak، Daily Prize و Backup با آزمون‌های قبل و بعد یکسان بماند؛ آزمون‌های وضعیت Daily Quest نیز سبز باشند.

- در نسخهٔ 2.8.0، نرمال‌سازی سوابق Custom Quest، اعتبارسنجی ایجاد مأموریت، قفل تکمیل دوباره و معیارهای بازشدن/متن پیشرفت Boss Quest به قرارداد مستقل TypeScript منتقل شدند. کاتالوگ Boss اکنون یک منبع واحد دارد و کنترل‌گر snapshot فعلی را ارائه می‌کند.
- در نسخهٔ 2.9.0، برنامهٔ اجرای تکمیل Custom Quest، ادعای جایزهٔ Boss و تصمیم‌های شواهد Goal به `src/features/quest-completion-plan.ts` منتقل شد. این ماژول صرفاً طرح خالص برمی‌گرداند؛ تغییر ذخیره و پاداش همچنان داخل تراکنش rollback موجود انجام می‌شود. شواهد تکراری پاداش تازه نمی‌گیرند، پیوند نامعتبر/کهنه قابل جداشدن است و شواهد نامعتبرِ غیرقابل‌ترمیم کل تراکنش را لغو می‌کنند.

### مرحلهٔ C — فعال‌سازی محتاطانهٔ IndexedDB (دروازهٔ تأیید در نسخهٔ 3.0.0)

- API مهاجرت اکنون گردش‌کار جداگانهٔ `preview → approve → migrate` را می‌طلبد؛ اجرای مهاجرت بدون تأیید صریح مجاز نیست.
- تأیید به fingerprint دقیق ذخیرهٔ قدیمی و تاریخ محلی وصل است؛ تغییر داده، عبور از نیمه‌شب، timestamp آینده یا نپذیرفتن هشدارها پیش از بازکردن IndexedDB رد می‌شود.
- عملیات هنوز کلیدهای localStorage را حذف یا بازنویسی نمی‌کند؛ امکان بازگشت عملیاتی فعلاً با حفظ مرجع قدیمی و فعال‌نکردن cutover تضمین می‌شود. حذف/برگرداندن فیزیکی رکوردهای IndexedDB در حالی که داده‌ها پس از مهاجرت تغییر کرده باشند، عمداً خودکار نشده است.
- آزمون تعاملی واقعی `tests/browser/indexeddb-transaction-test.js` در workflow CI اجرا می‌شود؛ آزمون قراردادی به‌تنهایی کافی نیست. در محیط محلی محدودشده با URLBlocklist این آزمون ممکن است اجرا نشود، و شکست آن نباید به‌عنوان موفقیت گزارش شود.
- cutover همچنان معطل تأیید مرورگر واقعی و سنجش رفتار پس از نصب/ارتقا و بازیابی Backup است.

**شرط عبور:** CI سبز، مهاجرت تکرارپذیر، بازیابی آزمایش‌شده و نبود پرداخت تکراری. تا آن زمان قطع `localStorage` ممنوع است.

### مرحلهٔ D — بومی‌سازی Android به اندازهٔ نیاز

- Java فعلی نگه‌داری می‌شود؛ در صورت نیاز به یک قابلیت پیچیده، API بومی کوچک و مستقل تعریف می‌شود.
- Kotlin فقط برای قابلیت جدید یا مهاجرت مرحله‌ای با آزمون آغاز می‌شود؛ ترجمهٔ کامل برنامه به Kotlin هدف مستقل نیست.
- SQLite تا زمانی که مدل گزارش‌گیری یا پرس‌وجوی بومی ضرورت نداشته باشد وارد نمی‌شود.

### مرحلهٔ E — سرویس AI و همگام‌سازی

- ابتدا نیاز و مدل تهدید نوشته شود؛ اگر همگام‌سازی سروری لازم شد، قرارداد API، احراز هویت، حذف/صدور داده و محدودسازی درخواست‌ها تعریف شود.
- FastAPI و Node.js گزینه‌اند، نه دو سرور هم‌زمان؛ یکی براساس نیاز واقعی انتخاب می‌شود.
- AI نباید بدون اجازه، دادهٔ پروفایل یا پیشرفت شخصی را ارسال کند.

- در نسخهٔ 3.0.0، API مهاجرت به پیش‌نمایش تأییدشده متصل شد؛ این gate ایمنی اجرا را بهبود می‌دهد اما به‌معنای فعال‌بودن IndexedDB برای UI نیست.

### مرحلهٔ F — فناوری‌های سنگین و چندزبانه

- Python برای ابزارهای توسعه و تحلیل، نه اجرای اصلی اپ.
- Canvas/WebGL یا Rust/WASM فقط با معیار عملکرد و نمونهٔ قابل‌اندازه‌گیری.
- ICU MessageFormat زمانی بررسی شود که plural/formatting چندزبانه به‌طور واقعی پیچیده شده باشد و تست‌های دری/RTL برای آن آماده باشند.

## ۴. محدودیت‌های شناخته‌شدهٔ فعلی

- `js/legacy/app-controller.js` هنوز کنترل‌گر بزرگ و چندمسئولیته است؛ نمایش UI و اجرای I/O ذخیره‌سازی آن‌جا مانده‌اند، اما در نسخهٔ 2.9.0 تصمیم‌های orchestration مربوط به Boss/Custom و Goal evidence نیز به طرح‌های TypeScript تبدیل شده‌اند. خود عملیات ذخیره و بازگردانی هنوز از آداپتور قدیمی استفاده می‌کند.
- IndexedDB و کد مهاجرت حاضرند؛ نسخهٔ 3.0.0 تأیید مهاجرت را به پیش‌نمایش و fingerprint مقید کرده است، اما ذخیره‌سازی زندهٔ عمومی هنوز `localStorage` است.
- فهرست و معیارهای پاداش‌های قدیمی یک‌باره به دادهٔ JSON یا TypeScript منتقل نشده‌اند؛ این کار باید بخش‌بخش و همراه سازگاری شناسه‌ها انجام شود.
- ساخت Web asset برای Android برابر ساخت APK نیست. APK واقعی باید در Android Gradle یا CI ساخته و خروجی آن بررسی شود.

این محدودیت‌ها تصمیم‌های آشکار معماری‌اند، نه نشانهٔ این‌که فناوری‌های به تعویق‌افتاده باید فوراً اضافه شوند.


### جلوه‌های بصری و انیمیشن — نسخهٔ 3.1.0

- `js/modules/visual-effects.js` یک ماژول تزئینی مستقل است: ذرات آرام، پیوندهای بسیار کم‌رنگ و حلقهٔ بازخورد اختیاری برای رویدادهای `system-quest-completed`، `system-level-up` و `system-achievement-unlocked` که هدف DOM را در `detail.target` یا `event.target` ارائه کنند.
- ماژول هیچ XP، Level، Rank یا Quest را تغییر نمی‌دهد و هیچ درخواست شبکه‌ای ندارد. تنها ذخیره‌سازی مجاز آن کلید مستقل ترجیحات بصری `system_v3_visual_settings` است. API آن `setEnabled(boolean)`، `setCelebrationsEnabled(boolean)`، `configure({ ambient, celebrations })`، `getSettings()` و `burstAt(x, y)` است.
- `css/features/visual-effects.css` از CSS تولیدی است؛ تغییرات باید در این فایل انجام شوند و سپس `npm run build:css` اجرا شود.
- حرکت با تنظیم سیستم `prefers-reduced-motion` خاموش می‌شود؛ رندر هنگام مخفی‌بودن صفحه متوقف می‌گردد، DPR حداکثر 1.5 و نرخ رندر حدود 30 FPS است. تعداد ذرات در موبایل پایین‌تر است.
- WebGL عمداً افزوده نشده است؛ برای این پس‌زمینهٔ دوبعدی سبک، هزینه و پیچیدگی آن توجیه ندارد.


### بازخورد ارتقاها و تنظیمات جلوه‌ها — نسخهٔ 3.2.0

- رخدادهای واقعی ارتقای سطح و رتبه پس از موفقیت تراکنش پیشرفت فرستاده می‌شوند؛ کارت بازخورد جداگانه برای Level Up و Rank Ascended نمایش داده می‌شود.
- پس از Claim موفق پاداشی از نوع Achievement، رویداد `system-achievement-unlocked` با نام نشان و کارت مرتبط پخش می‌شود. نشان‌ها از معیارهای موجود پیروی می‌کنند؛ این انیمیشن هیچ نشان یا امتیاز تازه‌ای ایجاد نمی‌کند.
- بخش Settings گزینه‌های «فضای کیهانی» و «جشن‌های ارتقا/دستاورد» را جداگانه کنترل می‌کند. فقط همین دو ترجیح در کلید مستقل `system_v3_visual_settings` ذخیره می‌شوند؛ XP، Rank، Quest و تاریخچه در این ماژول قابل تغییر نیستند.
- در حالت `prefers-reduced-motion` ذرات و حلقه‌های متحرک خاموش‌اند؛ اطلاعات پیشرفت همچنان به‌صورت پیام متنی قابل‌دسترس ارائه می‌شود. وقتی Canvas پشتیبانی نشود نیز پیام‌های milestone کار می‌کنند.
- این نسخه کد APK را تولید نمی‌کند؛ `npm run prepare:android` فقط assets وب را داخل پروژهٔ Android همگام می‌سازد.
