# SYSTEM Architecture Boundaries

## Source-of-truth rules

- Product release version: `VERSION` only; build scripts synchronize derived metadata.
- Progression domain: TypeScript under `src/core/`. XP/Level/Rank transitions and Quest completion must not be reimplemented in the view/controller layer.
- Dynamic achievement eligibility: `src/core/achievements.ts`. The legacy Rewards controller may provide a snapshot and render the result, but must not duplicate thresholds.
- Activity record validation, learning-evidence updates, lifetime-counter normalization and read-only aggregation: `src/core/activity-ledger.ts`. The legacy adapter may persist or render results but must not fork these domain rules.
- Reward identity and input validation: `src/core/reward-command.ts`.
- Custom Quest legacy normalization/draft validation/completion guard and Boss Quest catalogue/eligibility: `src/features/quest-command.ts` plus the canonical metadata in `src/data/quest-catalog.ts`.
- Seed/catalog validation: `src/data/seed-validation.ts`. JSON reference data are not assumed to be live runtime catalogs until explicitly wired and tested.
- CSS runtime bundle: generated from `scripts/build-css.js` and source fragments in `css/`.
- Service Worker app-shell list: generated by `scripts/build-sw.js`.
- Android WebView assets: generated by `scripts/sync-android-assets.js` after the web build.
- Persisted IDs, storage keys and backup shapes are compatibility contracts. Do not casually rename them.

## Layer ownership

1. `js/app.js` is the ES-module bootstrap and compatibility composition root. It exposes frozen TypeScript APIs to classic scripts and loads those scripts in the established order.
2. `src/core/` contains deterministic business rules without DOM or persistence side effects.
3. `src/features/` contains application commands that coordinate domain rules and storage adapters.
4. `src/storage/` owns IndexedDB transactions and explicit legacy migration planning. It does not automatically replace legacy saves.
5. `index.html` / `css/` own views and appearance. `css/system.css`, `dist/ts/`, `js/generated/`, and `sw.js` are generated outputs.
6. Android Java currently supplies WebView and OS integrations. It must not define a second XP/Quest implementation.
7. Provider calls and AI prompts remain optional; the app's local core must remain usable offline.

## Storage migration gate

The visible UI still uses legacy `localStorage`. The TypeScript IndexedDB schema and explicit migration APIs exist, but are not the live UI's single source of truth. A real-browser IndexedDB test must pass in the authorized CI runner before any production cutover. The migration must be replay-safe, preserve old localStorage, require a preview-bound approval, reject stale source fingerprints/date rollover before opening IndexedDB, and demonstrate recovery before a user-visible pathway is migrated. Warnings shown in the preview must be acknowledged. The runtime API is `preview() → approve(preview, options) → migrate(approval)`; migration is never invoked at startup.

## Transaction rollback shape integrity

The legacy compatibility transaction restores both persisted namespace values and the in-memory object shape. When a failed operation adds a new top-level player-state field or progress counter, rollback must delete that field before restoring the captured snapshot; restoring only existing snapshot keys can otherwise leave rejected state in memory. The regression contract is `tests/transaction-rollback-contract-test.js`.

## Safe change workflow

1. Update the source module or style fragment, not generated output.
2. Add or adjust a focused regression test.
3. Run `npm run build`, `npm test`, `npm run doctor`, and `npm run architecture:check`.
4. For browser-facing changes, run desktop and mobile Playwright checks.
5. Before Android build/release, run `npm run prepare:android` and confirm the web asset mirror matches the root sources.

## Gradual extraction priority

The main remaining structural risk is `js/legacy/app-controller.js`, which still contains UI glue and multiple product responsibilities. Extract small seams with regression tests; do not rewrite the entire file or storage format at once. Refer to [`ARCHITECTURE_ROADMAP_FA.md`](ARCHITECTURE_ROADMAP_FA.md) for the technology maturity map, deferred technologies and phase gates.


## Typed Daily Quest state boundary (v2.7.0)

The legacy Daily Quest localStorage payload contract is owned by `src/storage/legacy-daily-quest-state.ts`. It normalizes date-scoped completion records and creates compatibility storage entries, while the existing controller continues to orchestrate atomic writes through `SYSTEMStorage`. The storage keys remain `system_v2_quests` and `system_v2_quest_date`. This is a staged extraction, not an IndexedDB cutover. The source-of-truth decision stays `localStorage` until a real-browser IndexedDB integration test passes in an authorized environment.


## Typed Custom and Boss Quest rules (v2.8.0)

The compatibility controller no longer defines the Boss Quest catalogue or eligibility thresholds inline. `src/data/quest-catalog.ts` is the single source for stable Boss IDs, descriptions, rewards and thresholds; `src/features/quest-command.ts` evaluates progress from a small snapshot. The same feature module normalizes existing Custom Quest records, creates a validated draft, and rejects repeat completion attempts. The module is pure and does not write storage. The legacy controller continues to use existing save keys until a tested storage migration is approved.


## Typed Quest completion plans (v2.9.0)

`src/features/quest-completion-plan.ts` owns the decision contract for executing Custom Quest completions, Boss Quest claims, and evidence-based Goal outcomes. It returns pure plans and does not mutate player state or storage. The legacy controller must execute these plans only inside `runSystemTransaction`, using the existing reward/idempotency bridge and current storage keys. Invalid evidence aborts the parent transaction; a stale or branch-mismatched optional Goal link may be detached while a valid Custom Quest reward is kept; duplicate evidence cannot pay a second Goal bonus. The plan does not replace the existing rollback boundary or make localStorage writes atomic by itself.


## Preview-bound migration gate (v3.0.0)

`src/storage/legacy-migration.ts` now requires an explicit `LegacyMigrationApproval` before it can open the destination database. The approved fingerprint and local date must match a freshly rebuilt plan. A source save that changes after preview, an approval dated in the future, a local-date rollover, or unacknowledged preview warnings fail closed before any IndexedDB writes. The migration still leaves all legacy localStorage keys untouched. This gate protects sequencing; it does not mean IndexedDB has been switched on for normal application reads/writes.

## Visual effects boundary (v3.2.0)

`js/modules/visual-effects.js` owns decorative Canvas rendering, milestone toasts, and two visual preferences only. It may read/write the dedicated `system_v3_visual_settings` key, but must not read/write player progression records, calculate XP/Rank, grant rewards, or orchestrate Quest completion. Level/Rank events are emitted after successful legacy transactions; achievement feedback is emitted after a successful claim. Reduced-motion and page-visibility states remain runtime gates; CSS lives in `css/features/visual-effects.css` and is included through `scripts/build-css.js`. WebGL remains deferred until profiling demonstrates a real need.

## Typed curriculum persistence (schema v7)

`goal_curricula` stores validated Goal → Milestone definitions and their current evidence projection. `goal_evidence` is a separate append-only evidence ledger with a unique compound index on `(goalId, milestoneId, questId)`. When an opt-in caller completes a persisted Quest with `curriculumEvidence`, `completeQuestInDatabase()` reads the linked Goal and evidence identities and commits Player/Skill/Quest progress, XP history, activity, Goal snapshot and evidence row inside one `readwrite` transaction. Verification is evidence metadata, not an independent reward command; the result explicitly returns `curriculumRewardIssued: false`.

The live UI still uses legacy localStorage for main progression. `window.SYSTEMDurableCurriculumProgression` exposes the v7 transaction API for integration testing and staged migration, but does not copy, overwrite, or dual-write existing Goals. A production cutover still requires an explicit reviewed migration, adapter routing, and browser/device validation.

## Phase 9 — transactional progression contract

Quest completion is treated as a single durable state transition. The IndexedDB adapter must read the Player, Quest, canonical XP event, activity event identity and progress counters in one read-write transaction, then commit XP, Quest state, skill/stat progress, achievements, counters, activity history and optional Goal evidence together. A mixed set of completion markers is a consistency conflict and must fail closed; only a fully committed marker set is a safe replay. The pure TypeScript progression domain calculates XP/Level/Rank transitions and works on copies so validation failures do not mutate caller-owned state.

Regression contract: `tests/phase9-transactional-progression-contract-test.js`. This is a source-level contract test; it does not replace a real-browser IndexedDB concurrency/rollback test or Android WebView verification.
